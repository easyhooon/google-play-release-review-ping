# 폴링 워커를 어디에서 실행할까

이 문서는 개발 랩탑에서 연동을 검증하고, 워커를 홈서버나 클라우드 가상 머신(VM)으로 옮기는 기준을 설명합니다. 현재 구조에는 상태 파일을 보존하는 단일 상시 실행 장비가 적합합니다.

## 폴링 워커의 역할

`pnpm watch`로 실행한 Node.js 프로세스가 폴링 워커입니다. 별도의 중앙 서버는 없습니다. 워커는 다음 작업을 반복합니다:

1. `watch.config.json`에 등록한 앱과 트랙을 조회합니다.
2. Google Play API 응답을 `.data/state.json`의 이전 상태와 비교합니다.
3. 알림 대상 상태 전환을 Slack 또는 Discord로 전송합니다.
4. 관측한 상태를 `.data/state.json`에 저장합니다.

워커가 멈춘 동안에는 상태를 조회하지 않습니다. 다시 실행하면 현재 상태부터 조회하지만, 중간 상태 전환을 모두 복원하지는 못합니다.

## 개발 랩탑에서 연동 검증하기

처음에는 개발 랩탑을 워커 실행 장비로 사용합니다. 실제 앱, Google 자격증명, 웹훅까지 연결하는 통합 테스트에 적합합니다.

의존성과 설정 파일을 준비합니다:

```bash
pnpm install
cp watch.config.example.json watch.config.json
cp .env.example .env
```

`watch.config.json`에 실제 패키지명과 트랙을 입력하고 `.env`에 자격증명 경로와 웹훅을 설정합니다. 먼저 한 번만 조회합니다:

```bash
pnpm once
```

정상 조회되면 `checked`가 1 이상입니다. 첫 관측은 기준점만 저장하므로 `notifications=0`이 정상입니다. 이후 워커를 계속 실행합니다:

```bash
pnpm watch
```

이 명령은 터미널의 포그라운드 프로세스로 실행됩니다. 터미널을 닫거나 랩탑이 잠들면 워커가 멈춥니다. macOS에서 테스트하는 동안 잠자기를 막으려면 전원을 연결하고 다음 명령을 사용할 수 있습니다:

```bash
caffeinate -s pnpm watch
```

180초 주기는 짧은 연동 테스트에만 사용합니다. 상시 운영에서는 `pollIntervalSeconds`를 900 이상으로 설정합니다. 요청량 계산, 할당량 초기화와 403 복구 절차는 [`QUOTAS.md`](QUOTAS.md)를 참고하세요.

장기간 랩탑에서 운영해야 한다면 `launchd`에 등록해 로그인 후 자동 실행할 수 있습니다. `launchd`는 프로세스를 다시 시작할 수 있지만, 랩탑의 전원 종료와 잠자기까지 해결하지는 않습니다.

## 실행 환경 선택하기

운영 환경은 기존 장비 보유 여부와 필요한 가동률로 선택합니다:

| 환경 | 적합한 상황 | 장점 | 주의점 |
|---|---|---|---|
| 개발 랩탑 | 실제 앱 연동을 처음 검증할 때 | 추가 장비와 배포 작업이 없음 | 잠자기, 재부팅, 외부 이동 중 폴링 중단 |
| 홈서버 또는 네트워크 결합 스토리지(NAS) | 이미 24시간 가동하는 장비가 있을 때 | 현재 파일 기반 구조를 코드 변경 없이 사용 | 정전, 공유기, 회선 장애를 직접 관리 |
| 소형 클라우드 VM | 집 밖에서도 지속적인 폴링이 필요할 때 | 전원과 네트워크를 직접 관리하지 않음 | 월 비용, 보안 업데이트, 비밀 관리 필요 |
| 서버리스 또는 예약 작업 | 상태 저장소를 외부 서비스로 바꾼 뒤 | 실행 단위 운영과 확장에 유리 | 현재 로컬 상태 파일과 맞지 않아 코드 변경 필요 |

현재 단계에서는 다음 순서를 권장합니다:

1. 개발 랩탑에서 `pnpm watch`로 통합 테스트를 완료합니다.
2. 이미 상시 가동 중인 홈서버나 NAS가 있으면 그 장비로 옮깁니다.
3. 홈서버가 없거나 전원과 회선 장애의 영향을 줄여야 하면 소형 클라우드 VM을 사용합니다.

이 워커는 계산량과 네트워크 사용량이 작습니다. 높은 사양보다 상시 실행, 상태 파일 보존, 자동 재시작이 중요합니다.

## 홈서버로 옮기기

홈서버는 현재 구조와 가장 잘 맞습니다. Linux 장비에서는 `systemd` 같은 프로세스 관리자로 워커를 등록해 부팅 시 시작하고 실패 시 다시 실행합니다.

이전할 때는 다음 순서를 지킵니다:

1. 홈서버에 Node.js 22 이상과 pnpm을 설치합니다.
2. 저장소를 배포하고 `pnpm install --frozen-lockfile`을 실행합니다.
3. 홈서버에 `.env`와 `watch.config.json`을 만듭니다.
4. 랩탑 워커를 중지합니다.
5. 기존 `.data/state.json`을 홈서버의 같은 경로로 복사합니다.
6. 홈서버에서 `pnpm once`로 조회를 확인합니다.
7. 프로세스 관리자에서 `pnpm watch`를 시작합니다.

`.data/state.json`을 복사하면 이전 관측 상태를 이어서 비교할 수 있습니다. 복사하지 않으면 새 환경의 첫 관측을 기준점으로 저장하며 알림을 보내지 않습니다.

## 클라우드로 옮기기

현재 MVP에는 상시 실행되는 소형 Linux VM을 권장합니다. 로컬 디스크가 유지되므로 홈서버와 같은 방식으로 배포할 수 있습니다.

클라우드에서는 다음 항목을 추가로 준비합니다:

- 운영체제 보안 업데이트
- 재부팅 후 워커 자동 시작
- `.data/state.json`이 저장된 디스크의 보존과 백업
- 비밀 저장소 또는 런타임 서비스 계정을 통한 자격증명 관리
- 워커 실패 여부를 확인할 로그 또는 외부 모니터링

Google Cloud를 사용한다면 VM의 런타임 서비스 계정 이메일을 Play Console에 초대할 수 있습니다. 이 방식은 장기 서비스 계정 JSON 키를 VM에 복사하지 않아도 됩니다. 필요한 앱 읽기 권한만 부여합니다.

현재 구조에서 Cloud Run 같은 서버리스 환경은 첫 이전 대상으로 권장하지 않습니다. 인스턴스 로컬 파일이 영속적이지 않고 여러 인스턴스가 동시에 실행될 수 있기 때문입니다. 서버리스로 이전하려면 상태 저장소를 데이터베이스나 객체 저장소로 바꾸고, 동시 실행 잠금도 추가해야 합니다.

## 워커를 안전하게 이전하기

이전 중에는 한 개의 워커만 실행합니다. 두 워커가 같은 앱을 동시에 감시하면 각각 다른 상태 파일을 사용해 알림이 중복될 수 있습니다.

안전한 이전 순서는 다음과 같습니다:

1. 기존 워커를 중지합니다.
2. `.data/state.json`과 설정을 새 장비로 복사합니다.
3. 새 장비에서 `pnpm once`를 실행합니다.
4. `checked` 값과 오류 로그를 확인합니다.
5. 새 장비에서 `pnpm watch`를 시작합니다.

서비스 계정 JSON과 웹훅 URL은 저장소에 커밋하지 않습니다. 환경별 보안 기준은 [`SECURITY.md`](SECURITY.md)를 참고하세요.
